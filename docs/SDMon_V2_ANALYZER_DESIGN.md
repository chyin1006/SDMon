# SDMon V2 Analyzer Design

This document defines the SDMon V2 Analyzer at the framework design level. It does not define concrete implementation code and does not change the V1.1 baseline.

## 1. Analyzer Goals

The Analyzer turns Rule Engine output into structured behavior analysis that administrators can understand.

Primary goals:

- Read Findings generated by the Rule Engine.
- Generate behavior timelines.
- Aggregate repeated events.
- Calculate risk scores.
- Generate administrator-readable behavior explanations.
- Organize evidence for later reporting.
- Support correlation analysis across multiple behavior signals.
- Avoid final malware classification.
- Provide behavior explanation and risk hints only.

The Analyzer should explain what was observed during the collection window. It should not claim that an Agent is malicious or benign in absolute terms.

## 2. Analyzer Position In The Framework

Analyzer sits after the Rule Engine and before Reporter.

Framework data flow:

```text
Profile
  ↓
Sensor
  ↓
Raw Event
  ↓
Normalized Event
  ↓
Rule Engine
  ↓
Finding
  ↓
Analyzer
  ↓
Timeline / Summary / Risk Score
  ↓
Reporter
```

Layer responsibilities:

- Profile defines the target context.
- Sensor collects evidence in a read-only way.
- Raw Event stores original observations.
- Normalized Event provides a consistent event shape.
- Rule Engine produces Findings from normalized events and Profile context.
- Analyzer aggregates, deduplicates, correlates, scores, and explains Findings.
- Reporter renders Analyzer output into final human-readable or machine-readable reports.

The Analyzer is an interpretation layer. It does not collect evidence and does not render final report layouts.

## 3. Analyzer Responsibilities

Analyzer responsibilities include:

- Finding aggregation.
- Finding deduplication.
- Timeline generation.
- Risk score calculation.
- Confidence calculation.
- Behavior summary generation.
- Correlation analysis.
- Evidence organization.
- Report data output.

### finding aggregation

The Analyzer groups Findings by target, process, path, endpoint, Rule, severity, and time window.

Aggregation helps administrators see behavior patterns rather than long lists of repeated low-level events.

### finding deduplication

The Analyzer merges repeated Findings that represent the same behavior signal.

A repeated access to the same sensitive path by the same process in a short time window should usually become one summarized Finding with evidence count and first/last seen timestamps.

### timeline generation

The Analyzer builds a time-ordered view of important events.

The timeline should include process, file, network, persistence, privilege, and correlation events when available.

### risk score calculation

The Analyzer calculates an explainable risk score based on Rule severity, Profile context, evidence count, confidence, and correlations.

Risk score is a review aid, not a malware verdict.

### confidence calculation

The Analyzer estimates confidence separately from risk.

Confidence reflects how reliable the evidence is, not how severe the behavior is.

### behavior summary generation

The Analyzer produces a structured summary that describes what the target Agent did during the observation window.

### correlation analysis

The Analyzer combines related Findings into higher-level behavior explanations when the evidence supports it.

### evidence organization

The Analyzer keeps evidence references structured and traceable.

It should reference source events and artifacts without copying unrelated personal content into analysis output.

### report data output

The Analyzer emits structured data for Reporter components.

Reporter should be able to render text, HTML, CSV, and JSON outputs from Analyzer data without re-parsing raw logs.

## 4. What Analyzer Does Not Do

The Analyzer is not responsible for:

- Collecting data.
- Running Sensors.
- Modifying Rules.
- Generating final HTML or text report styling.
- Deleting target Agent files.
- Quarantining target Agent files.
- Stopping target Agent processes or services.
- Unloading LaunchDaemons or LaunchAgents.
- Blocking network connections.
- Making final malware classification.
- Uploading reports or analysis results.

The Analyzer must preserve SDMon's transparent, read-only, observation-window-based model.

## 5. Input Data Structures

Analyzer inputs should be structured and traceable.

Primary inputs:

- Normalized Events
- Findings
- Profile Metadata
- Rule Metadata

### Normalized Events

Normalized Events represent platform-neutral observations derived from Sensor output.

Example event categories:

- process event
- file event
- network event
- launchd event
- privilege event
- system event

Normalized Event fields may include:

```text
EVENT_ID
TIMESTAMP
SOURCE_SENSOR
EVENT_TYPE
PROCESS_NAME
PID
USER
ACTION
TARGET
FILE_PATH
ENDPOINT
BYTES_IN
BYTES_OUT
RAW_SOURCE
RAW_REFERENCE
```

### Findings

Findings are Rule Engine outputs.

Expected Finding fields include:

```text
FINDING_ID
RULE_ID
PROFILE_ID
TIMESTAMP
RISK_LEVEL
RISK_SCORE
CONFIDENCE
TITLE
DESCRIPTION
EVIDENCE
RECOMMENDATION
TAGS

```

### Profile Metadata

Profile Metadata provides target context.

Useful Profile fields include:

```text

TARGET_PATHS

TARGET_ENDPOINTS

```

### Rule Metadata

Useful Rule fields include:


## 6. Output Data Structures

Analyzer outputs should be structured so Reporters can render them without redoing analysis.

Required V2 Analyzer outputs:

- `timeline.csv`
- `analysis.json`
- `risk_summary.json`
- `report_data.json`

### timeline.csv

Time-ordered analysis output for review and reporting.

### analysis.json

Structured complete analysis result.

Recommended content:

```text
run metadata
profile metadata
finding groups
deduplicated findings
correlations
evidence references
limitations
```

### risk_summary.json

Risk score and scoring explanation.

Recommended content:

```text
overall risk score
overall risk level
confidence summary
score contributors
correlation contributors
sensitive asset contributors
limitations
```

### report_data.json

Reporter-ready data model.

Recommended content:

```text
summary blocks
finding sections
timeline references
risk summary
profile labels
i18n keys
evidence references
administrator attention items
```

Reporters should consume these outputs to produce `summary.txt`, `findings.txt`, `timeline.csv`, `report.html`, and future formats.

## 7. Timeline Design

The timeline should give administrators a chronological view of meaningful behavior.

Recommended `timeline.csv` fields:

```text
TIMESTAMP
PROFILE_ID
PROCESS_NAME
PID
EVENT_TYPE
ACTION
TARGET
RISK_LEVEL
RULE_ID
SUMMARY
```

Field notes:

- `TIMESTAMP` records when the event or Finding occurred.
- `PROFILE_ID` links the event to the active Profile.
- `PROCESS_NAME` identifies the process when available.
- `PID` identifies the process instance when available.
- `EVENT_TYPE` describes the normalized event category.
- `ACTION` describes the observed action.
- `TARGET` describes the file, endpoint, launch item, or object affected.
- `RISK_LEVEL` records the highest associated risk level.
- `RULE_ID` links the timeline row to the triggering Rule when applicable.
- `SUMMARY` provides a compact behavior explanation.

Timeline principles:

- Keep rows evidence-backed.
- Avoid duplicating every raw event when aggregation is clearer.
- Preserve enough detail for an administrator to trace back to evidence.
- Mark inferred or correlated rows clearly.

## 8. Risk Score Calculation Design

Risk Score may combine multiple factors.

Recommended factors:

- Rule Level
- Rule Weight
- Profile Weight
- Evidence Count
- Correlation Count
- Confidence
- Sensitive Asset Weight

Conceptual baseline formula:

```text
risk_score = base_rule_score
           * rule_weight
           * profile_weight
           * confidence_factor
           + evidence_bonus
           + correlation_bonus
           + sensitive_asset_bonus
```

Recommended base scores:

| Rule Level | Base Score |
| --- | --- |
| critical | 90 |
| high | 70 |
| medium | 40 |
| low | 10 |
| info | 0 |

Design notes:

- V2 should define a simple, explainable baseline formula first.
- V2 should not require complex scoring algorithms before the macOS framework is stable.
- Scores should be capped at a maximum value such as 100.
- Score contributors should be listed in `risk_summary.json`.
- Risk score should not be treated as a malware verdict.
- Missing evidence should reduce confidence or appear as a limitation.

## 9. Correlation Analysis

Correlation analysis combines related Findings into higher-level behavior explanations.

Required correlation scenarios to design:

- Sensitive file access + network upload.
- LaunchDaemon persistence + high-privilege process.
- Unexpected process + external connection.
- Browser credential access + large traffic transfer.
- SSH Key access + external connection.

### sensitive file access + network upload

This correlation indicates that a target accessed sensitive data and later transferred data externally during the observation window.

The Analyzer should preserve both evidence references and avoid claiming exfiltration unless the evidence supports that conclusion.

### LaunchDaemon persistence + high-privilege process

This correlation indicates that the target has a persistence mechanism and runs with elevated privileges.

The Analyzer should explain that this may be expected for enterprise Agents but still deserves administrator awareness.

### unexpected process + external connection

This correlation indicates that a process not expected by the Profile made an external connection.

The Analyzer should show why the process was unexpected and which endpoint was contacted.

### browser credential access + large traffic transfer

This correlation indicates a sensitive browser data signal and a notable traffic signal in the same window.

The Analyzer should keep wording evidence-first and avoid unsupported intent claims.

### SSH Key access + external connection

This correlation indicates SSH key path access and outbound connection behavior.

The Analyzer should identify source process, key path evidence, endpoint evidence, and timing relationship.

Correlation design principles:

- Correlations should be optional and explainable.
- Correlations should cite contributing Findings.
- Correlations should not hide original Findings.
- Correlations should not claim malicious intent without evidence.
- V2 should design the model but not require complex correlation implementation immediately.

## 10. Behavior Summary

The Analyzer should output a behavior summary that administrators can understand quickly.

The behavior summary should answer:

- Whether the target Agent was running.
- Which processes were observed.
- Which addresses or endpoints were contacted.
- Which sensitive paths were accessed.
- Whether persistence items were present.
- Whether high-risk behavior was observed.
- What administrators should review.

Recommended summary fields:

```text
PROFILE_ID
PROFILE_NAME
COLLECTION_WINDOW
TARGET_RUNNING_STATUS
OBSERVED_PROCESSES
OBSERVED_ENDPOINTS
OBSERVED_SENSITIVE_PATHS
OBSERVED_PERSISTENCE
HIGH_RISK_BEHAVIORS
ADMIN_ATTENTION_ITEMS
LIMITATIONS
```

Summary principles:

- Prefer observed facts over speculation.
- Clearly distinguish observed, not observed, and unknown.
- Explain that absence of evidence during the collection window does not prove behavior never occurs.
- Include administrator attention items without prescribing destructive action.

## 11. Confidence Design

Confidence is not the same as Risk.

Risk describes potential impact or severity.

Confidence describes how reliable the evidence is.

Examples:

- `pcap` and `lsof` both matching the same endpoint should increase confidence.
- A single vague `fs_usage` record should have lower confidence.
- Multiple Sensors cross-validating the same behavior should increase confidence.
- Missing or partial logs should reduce confidence.

Recommended confidence factors:

- Number of independent Sensors supporting the Finding.
- Evidence quality.
- Event specificity.
- Repetition across time.
- Match precision.
- Raw evidence availability.

Recommended confidence levels:

- high
- medium
- low
- unknown

Confidence output should explain why a behavior was assigned a given confidence level.

## 12. Analyzer And Reporter Relationship

Analyzer outputs structured data only.

Reporter is responsible for rendering structured data into final artifacts:

- `summary.txt`
- `findings.txt`
- `timeline.csv`
- `report.html`

Analyzer responsibilities:

- Produce timeline data.
- Produce deduplicated Findings.
- Produce risk summaries.
- Produce behavior summaries.
- Produce report-ready structured data.

Reporter responsibilities:

- Select output format.
- Apply language resources.
- Apply templates.
- Render text, HTML, CSV, JSON, or future formats.
- Present evidence and limitations clearly.

The Reporter should not need to re-parse raw logs when Analyzer outputs are available.

## 13. Internationalization

Analyzer internal fields should use stable English identifiers.

Examples:

- `PROFILE_ID`
- `RULE_ID`
- `EVENT_TYPE`
- `RISK_LEVEL`
- `CONFIDENCE`
- `ADMIN_ATTENTION_ITEMS`

Final Chinese or English display should be handled by Reporter and i18n resources.

Language strategy:

- `REPORT_LANG=auto`
- `zh-CN`
- `en-US`

Internationalization principles:

- Analyzer output should be language-neutral where practical.
- Reporter maps Analyzer fields and message keys to the selected language.
- Chinese systems should receive Chinese report text when `REPORT_LANG=auto`.
- Non-Chinese systems should receive English report text when `REPORT_LANG=auto`.
- Missing translations should fall back to English.

## 14. What V2 Does Not Do

V2 Analyzer does not include:

- Automatic remediation.
- Final malware attribution.
- Network submission of analysis results.
- Report upload.
- Hidden employee monitoring.
- Agent deletion.
- Agent quarantine.
- Agent stop or unload actions.
- Security software bypass.

Analyzer output should help administrators review evidence. It should not take action against the target Agent.

## 15. V1.1 To V2 Migration

V1.1 analysis logic currently lives in reporting-oriented scripts such as `summary.sh` and `findings.sh`.

In V2, analysis logic should gradually move into `analyzers/`.

Migration examples:

```text
bin/summary.sh -> analyzers/summary_analyzer.sh
bin/findings.sh -> analyzers/finding_analyzer.sh
```

Additional future Analyzer modules may include:

```text
analyzers/timeline_analyzer.sh
analyzers/risk_score_analyzer.sh
analyzers/correlation_analyzer.sh
analyzers/evidence_analyzer.sh
```

Migration principles:

1. Preserve V1.1 as the runnable baseline.
2. Keep root-level command wrappers unchanged during early migration.
3. Move behavior interpretation out of Reporter scripts and into Analyzer modules.
4. Keep Reporters focused on rendering Analyzer output.
5. Keep raw logs immutable during analysis.
6. Make Analyzer outputs structured and repeatable.
7. Add `timeline.csv`, `analysis.json`, `risk_summary.json`, and `report_data.json` when the V2 pipeline is ready.
8. Update README only after the V2 Analyzer workflow is runnable and tested.

This migration keeps V1.1 stable while making V2 analysis easier to test, extend, and render in multiple report formats.
