# SDMon V2 Reporter Design

This document defines the SDMon V2 Reporter, also called the report engine, at the framework design level. It does not define concrete implementation code and does not change the V1.1 baseline.

## 1. Reporter Goals

Reporter is responsible for rendering Analyzer output into final reports.

Reporter does not perform analysis.

Reporter goals:

- Convert structured Analyzer output into final report artifacts.
- Make SDMon results understandable for administrators.
- Preserve evidence references and limitations.
- Support multiple output formats.
- Keep report templates separate from analysis logic.
- Support internationalized report text.

Supported V2 output formats:

- txt
- html
- json
- csv

Future output formats:

- pdf
- markdown

Reporter should not re-interpret raw evidence. It should display analysis results produced by Analyzer.

## 2. Reporter Position In The Framework

Reporter sits after Analyzer and before final user-facing artifacts.

Framework flow:

```text
Profile
  ↓
Sensor
  ↓
Rule Engine
  ↓
Analyzer
  ↓
Reporter
  ↓
Final Report
```

Layer responsibilities:

- Profile defines target context.
- Sensor collects evidence.
- Rule Engine generates Findings from normalized events.
- Analyzer aggregates Findings, builds timeline, calculates risk, and prepares structured report data.
- Reporter renders structured data into final formats.
- Final Report is the output reviewed by administrators or imported into other tools.

Reporter should depend on Analyzer outputs, Profile metadata, templates, and i18n resources. It should not depend on raw Sensor logs when structured Analyzer output is available.

## 3. Reporter Responsibilities

Reporter responsibilities include:

- Summary Report
- Findings Report
- Timeline Report
- HTML Dashboard
- JSON Export
- CSV Export

### Summary Report

Produces a short text report that administrators can read quickly.

### Findings Report

Produces a detailed finding-oriented report with evidence and recommendations.

### Timeline Report

Produces a chronological view of important events.

### HTML Dashboard

Produces a browser-readable report with overview, timelines, risk sections, finding details, evidence references, and profile metadata.

### JSON Export

Produces machine-readable output for automation, APIs, CI, SOC, SIEM, or later analysis.

### CSV Export

Produces tabular output for Excel, PowerBI, Splunk, ELK, and similar workflows.

## 4. Reporter Inputs

Reporter consumes structured output from Analyzer.

Required inputs:

- `analysis.json`
- `risk_summary.json`
- `timeline.csv`
- `finding.json`
- profile metadata

### analysis.json

Complete structured analysis result.

Expected content may include:

```text
run metadata
profile metadata
finding groups
correlations
limitations
evidence references
administrator attention items
```

### risk_summary.json

Structured risk scoring output.

Expected content may include:

```text
overall risk level
overall risk score
confidence
score contributors
correlation contributors
sensitive asset contributors
```

### timeline.csv

Timeline generated by Analyzer.

Reporter may copy it into the final reports directory and render it in HTML.

### finding.json

Structured Finding records.

Expected content may include:

```text
finding id
rule id
profile id
timestamp
title
description
evidence
recommendation
risk
confidence
tags
source event
```

### profile metadata

Target scope and report context.

Expected content may include:

```text
PROFILE_ID
PROFILE_NAME
PROFILE_PLATFORM
PROFILE_CATEGORY
REPORT_LANG
TARGET_PROCESSES
TARGET_PATHS
TARGET_ENDPOINTS
```

## 5. Reporter Outputs

Reporter should write final artifacts into a dedicated report directory.

Recommended output directory:

```text
reports/
  summary.txt
  findings.txt
  timeline.csv
  analysis.json
  report.html
  report.json
  assets/
```

Output purpose:

- `summary.txt`: short administrator-readable summary.
- `findings.txt`: detailed text findings.
- `timeline.csv`: chronological event table.
- `analysis.json`: copied or normalized Analyzer output for traceability.
- `report.html`: browser-readable dashboard.
- `report.json`: consolidated machine-readable report.
- `assets/`: CSS, static images, client-side support files, or future report assets.

Output rules:

- Reports should be generated from Analyzer output.
- Reports should preserve evidence references.
- Reports should clearly state limitations.
- Reports should avoid overstating conclusions.
- Generated reports from real runs should not be committed to the repository.

## 6. Summary Report

The Summary Report should let an administrator understand the run at a glance.

Recommended content:

- Collection time.
- Target name.
- Runtime or observation window.
- Profile.
- Risk Level.
- Risk Score.
- Confidence.
- Finding count.
- Recommended actions.

Suggested structure:

```text
SDMon Summary
Target: <profile name>
Profile: <profile id>
Collection Window: <start> - <end>
Risk Level: <level>
Risk Score: <score>
Confidence: <confidence>
Findings: <count>

Administrator Attention:
- <action item 1>
- <action item 2>

Limitations:
- <limitation 1>
```

Summary principles:

- Keep it short.
- Prefer observed facts.
- Separate observed, not observed, and unknown.
- Include evidence limitations.
- Avoid malware verdicts.
- Avoid remediation actions that modify the target Agent.

## 7. Findings Report

The Findings Report should show each Finding in a reviewable format.

Each Finding should include:

- Title
- Description
- Evidence
- Recommendation
- Rule
- Profile
- Timestamp
- Risk

Recommended Finding section shape:

```text
[Risk Level] Title
Timestamp: <timestamp>
Profile: <profile id>
Rule: <rule id>
Risk: <risk level> / <risk score>
Confidence: <confidence>

Description:
<description>

Evidence:
<evidence reference>

Recommendation:
<recommendation>
```

Findings Report principles:

- Group by severity when useful.
- Preserve Finding IDs and Rule IDs.
- Keep evidence references traceable.
- Avoid copying unrelated personal content.
- State whether repeated events were aggregated.
- Keep recommendations review-oriented and non-destructive.

## 8. Timeline Report

The Timeline Report should present events in chronological order.

Recommended fields:

- Time
- Process
- Action
- Target
- Result
- Risk

Suggested CSV fields:

```text
Time,Process,Action,Target,Result,Risk
```

Timeline principles:

- Sort by time ascending.
- Keep one row per meaningful event or aggregated Finding.
- Preserve links to Rule ID and evidence where possible.
- Mark correlated or inferred events clearly.
- Avoid dumping every raw log line when Analyzer has already aggregated events.

## 9. HTML Dashboard

The HTML Dashboard should provide a readable browser-based report.

Recommended dashboard sections:

- Overview
- Timeline
- Risk Distribution
- Finding List
- Evidence
- System Information
- Profile Information

### Overview

Shows target name, collection window, profile, risk level, risk score, confidence, and finding count.

### Timeline

Shows a searchable or readable chronological table of important events.

### Risk Distribution

Shows counts by risk level and optionally counts by behavior category.

### Finding List

Shows findings grouped by severity, category, rule, or process.

### Evidence

Shows evidence references, source files, event IDs, and limitations.

### System Information

Shows minimal system metadata needed to interpret the report.

### Profile Information

Shows selected Profile ID, name, platform, category, target processes, target paths, and configured endpoints.

HTML Dashboard principles:

- It should work as a static file.
- It should not require a web server.
- It should not fetch remote scripts or assets by default.
- It should render from local report data.
- It should support light and dark themes over time.

## 10. JSON Report

`report.json` is the consolidated machine-readable report.

It should support downstream workflows such as:

- CI
- SOC
- SIEM
- API
- secondary analysis

Recommended top-level structure:

```text
report_version
sdmon_version
run_metadata
profile
risk_summary
findings
timeline
correlations
evidence
limitations
```

JSON Report principles:

- Use stable field names.
- Preserve IDs for Profile, Rule, Finding, and source events.
- Avoid embedding unrelated personal content.
- Include schema version or report version.
- Keep report data suitable for automation.

## 11. CSV Report

CSV output should make SDMon results easy to inspect in tabular tools.

Target workflows:

- Excel
- PowerBI
- Splunk
- ELK

Recommended CSV files may include:

```text
timeline.csv
findings.csv
risk_summary.csv
```

CSV principles:

- Use stable headers.
- Prefer one logical record per row.
- Escape values safely.
- Preserve timestamps in a sortable format.
- Include IDs for traceability.

## 12. Internationalization

Reporter supports report language selection.

Supported language modes:

- `REPORT_LANG=auto`
- `zh-CN`
- `en-US`

Language behavior:

- Chinese systems should output Chinese reports by default.
- English or non-Chinese systems should output English reports by default.
- Command line options may force the language.
- Profile or configuration may also force the language.

Reporter i18n responsibilities:

- Resolve display strings from i18n resources.
- Render the same Analyzer data in different languages.
- Keep internal IDs stable across languages.
- Fall back to English when a translation is missing.

Recommended i18n resources:

```text
i18n/zh-CN/messages.conf
i18n/en-US/messages.conf
```

Reporter should not require Analyzer to produce localized prose.

## 13. Theme

Reporter should support theme design for human-readable reports.

Initial theme:

- Light Theme
- Dark Theme

Future theme support:

- Company Branding

Theme principles:

- Themes should not affect analysis data.
- Themes should be separate from report data.
- Themes should be static and local by default.
- Company branding should be configurable without modifying Analyzer output.

## 14. Report Template

Reporter and templates should be separated.

Recommended template directories:

```text
templates/
  txt/
  html/
  json/
```

Template responsibilities:

- Define report layout.
- Define section ordering.
- Define static labels through i18n keys.
- Define HTML structure and local assets.

Reporter responsibilities:

- Load templates.
- Load Analyzer data.
- Resolve language strings.
- Render final files.

Templates should not collect evidence, analyze events, or modify Profile and Rule data.

## 15. Reporter And Analyzer Relationship

Analyzer outputs structured data.

Reporter only displays structured data.

Analyzer responsibilities:

- Generate Findings.
- Generate timeline.
- Calculate risk score.
- Calculate confidence.
- Generate behavior summary.
- Output `analysis.json`, `risk_summary.json`, and report-ready data.

Reporter responsibilities:

- Render `summary.txt`.
- Render `findings.txt`.
- Render `timeline.csv`.
- Render `report.html`.
- Render `report.json`.
- Apply templates, themes, and language resources.

Reporter should not re-run Analyzer logic.

## 16. What Reporter Does Not Do

Reporter is not responsible for:

- Collecting data.
- Analyzing data.
- Modifying Rules.
- Modifying Profiles.
- Uploading reports.
- Starting or stopping Sensors.
- Deleting, quarantining, stopping, or modifying target Agents.

Reporter should remain a rendering and export layer.

## 17. What V2 Does Not Do

V2 Reporter does not include:

- Online report viewing.
- Web Server.
- Automatic OSS upload.
- Automatic email sending.
- Automatic Slack sending.
- Automatic Teams sending.
- Automatic DingTalk sending.
- Remote report hosting.
- Hidden report transmission.

Reports should remain local artifacts unless a user explicitly shares them outside SDMon.

## 18. V1.1 To V2 Migration

V1.1 currently has report-related logic in scripts such as:

```text
summary.sh
findings.sh
```

In V2, report rendering should gradually migrate into:

```text
reporters/
```

Migration examples:

```text
bin/summary.sh -> reporters/text/summary.sh
bin/findings.sh -> reporters/text/findings.sh
```

Migration principles:

1. Preserve V1.1 as the runnable baseline.
2. Keep root-level command wrappers stable during early migration.
3. Move behavior analysis out of Reporter scripts and into Analyzer modules.
4. Keep Reporter focused on rendering Analyzer output.
5. Add HTML report rendering only after Analyzer output is structured.
6. Keep generated reports out of source control.
7. Update README after V2 reporting is runnable and tested.

This migration keeps existing reports familiar while preparing SDMon for structured text, HTML, JSON, and CSV outputs.

## 19. Final Directory Recommendation

Recommended long-term report-related directories:

```text
reporters/
templates/
i18n/
assets/
```

Directory responsibilities:

- `reporters/`: report rendering modules.
- `templates/`: report templates for text, HTML, JSON, and future formats.
- `i18n/`: language resources.
- `assets/`: local static assets for HTML reports and themes.

These directories should remain separate from Sensors, Rules, Profiles, and Analyzers.

## 20. Long-term Roadmap

Long-term Reporter expansion may support:

- SOC Dashboard
- SIEM Export
- FortiSIEM
- Splunk
- QRadar
- Microsoft Sentinel
- Elastic
- OpenSearch

Long-term design principles:

- Export should use structured Analyzer data.
- SIEM integrations should not require changing Sensors or Rules.
- Integrations should be explicit and user-controlled.
- No automatic upload should be enabled by default.
- Report formats should remain evidence-first and read-only.
